# 整合規則：只統一會造成 bug 的地方

**除了這份列的項目，其他都自由發揮。** 介面設計、顏色、排版、要加什麼功能、演算法怎麼寫、用哪個 AI、提示詞怎麼下、自己資料夾裡怎麼分檔，都由各自決定。

下面每一條都是**預測合併時最可能壞掉的點**。每條都寫了：不統一會怎麼壞、要統一成什麼、`node check.js` 會不會自動抓。

---

## 資料（A 輸出、B C D 讀取）

### 1. 單位一律公尺，Revit 要換算　｜負責：A　｜check.js：會抓
- **會怎麼壞**：Revit API 內部單位是**英尺**，面積是平方英尺。沒換算的話，30 m 的走廊會變成 98，全部判成不符合。
- **統一**：長度用公尺，面積用平方公尺。用 `UnitUtils.ConvertFromInternalUnits(值, UnitTypeId.Meters)` 換算。
- **自動檢查**：用房間外框算面積，跟 `area_m2` 比對，差到 10.76 倍（英尺換算的倍數）就報錯。

### 2. 座標用 Revit 的方向（y 向上＝北）　｜負責：A、D　｜check.js：不會抓
- **會怎麼壞**：網頁的 y 軸向下，Revit 的 y 軸向上。不翻轉的話，平面圖會上下顛倒，北向箭頭也會指錯。
- **統一**：資料裡一律存 Revit 座標，**只有畫圖時翻轉**。目前介面已經處理好，D 改畫圖時要保留 `src/page.html` 裡的 `Y()` 函式。

### 3. ElementId 一律用文字　｜負責：A　｜check.js：會抓
- **會怎麼壞**：Revit 2024 的 ElementId 是長整數。有人存成數字 `523105`、有人存成文字 `"523105"` 的話，比對時會判成不相等，結果找不到房間，畫面空白。
- **統一**：所有 `element_id`、`door_ids`、`stair_id` 都存成文字，例如 `"523105"`。

### 4. JSON 存成 UTF-8，不要有 BOM　｜負責：A，以及任何寫 JSON 的人　｜check.js：會抓
- **會怎麼壞**：C# 的 `Encoding.UTF8` 和 PowerShell 5.1 的 `Out-File`，會在檔案開頭偷偷加三個看不見的字元（BOM），讀取時會報錯 `Unexpected token`。
- **統一**：C# 用 `new UTF8Encoding(false)`；PowerShell 用 `[IO.File]::WriteAllText(路徑, 內容)`。

### 5. 不知道就填 `null`，不要填 0、空字串、-1　｜負責：A、B　｜check.js：部分會抓
- **會怎麼壞**：門寬不知道卻填 0，程式會當成門寬真的是 0 m，判成不符合。計畫書規定缺資料要標「模型資料不足」，不是不合格。
- **統一**：不確定的值一律 `null`。

### 6. 欄位名稱照 `docs/data-contract.md`，可以加、不改名　｜負責：所有人　｜check.js：會抓
- **會怎麼壞**：A 寫 `doorIds`，B 讀 `door_ids`，讀到的是空值，程式直接當掉。
- **統一**：用小寫加底線（snake_case）。可以自由**加**新欄位；要**改名或刪除**欄位，先在群組講。

### 7. 外框不重複第一點，順時針、逆時針都可以　｜負責：A 輸出、B D 讀取　｜check.js：不會抓
- **會怎麼壞**：A 照 Revit 的邊界順序輸出，B 或 D 卻假設「第 0 點是左上角」，畫出來或算出來都會錯。
- **統一**：讀外框的人要自己算最大、最小值，不能假設點的順序。

### 8. 一間房可能有好幾個門　｜負責：A、B　｜check.js：會抓
- **統一**：`door_ids` 一定是陣列，只有一個門也寫成 `["700105"]`。B 要不要考慮全部的門，可以自己決定。

## 程式（B、C 的 engine）

### 9. 函式的輸入和輸出不改　｜負責：B、C　｜check.js：會抓
- **會怎麼壞**：`engine/review.js` 用固定的方式呼叫 B 和 C 的函式。改了參數或回傳的格式，整個檢討就會當掉。
- **統一**：以下四個函式的**參數和回傳格式**不改。函式內部怎麼寫完全自由，也可以另外加新的函式。

| 誰 | 函式 | 參數 | 回傳 |
|---|---|---|---|
| B | `measureRoom` | `(room, snapshot)` | `facts` 物件；缺資料時回傳 `{ missing: "原因" }` |
| C | `walkLimit` | `(settings)` | `{ limit, rules, pending }` |
| C | `judgeRoom` | `(room, facts, lim, P, corridors)` | `{ status, reasons, legal, hints }` |
| C | `judgeCorridor` | `(corridor, settings, habitableArea)` | 走廊結果物件 |

### 10. engine 檔案的外殼寫法不改　｜負責：B、C　｜check.js：會抓
- **會怎麼壞**：`build.js` 會把 engine 的檔案原封不動塞進網頁。網頁不認得 `import`、`export`、`require("套件")`，加了就會整頁空白。
- **統一**：保留 `(function (root) { ... })(this)` 這個外殼。不要用 `import`、`export`，也不要裝 npm 套件。需要的功能自己寫，或請 AI 寫在檔案裡。

### 11. engine 裡不用時間和亂數　｜負責：B、C　｜check.js：會抓
- **會怎麼壞**：同一個模型算兩次結果不一樣，違反計畫書「相同輸入得到相同結果」的原則，也沒辦法核對。
- **統一**：engine 裡不用 `Date.now()`、`new Date()`、`Math.random()`。時間由 `review.js` 統一處理。

### 12. 小數比較用原始值，顯示時才四捨五入　｜負責：B、C　｜check.js：不會抓
- **會怎麼壞**：30.004 m 四捨五入成 30.00 以後才比，會判成「剛好符合」，但實際上超過了。
- **統一**：判定時用原始數值比；輸出存兩位小數；畫面顯示時再取一位。不要用 `===` 比較兩個算出來的小數。

### 13. 狀態文字只有四種，一字不差　｜負責：C、D　｜check.js：會抓
- **會怎麼壞**：畫面靠這幾個字決定顏色和符號。打成「不合格」或「需確認」，那間房就不會顯示顏色，篩選也會失效。
- **統一**：`符合`、`不符合`、`需人工確認`、`模型資料不足`。

### 14. 用到的規則編號，`regs/rules.json` 裡一定要有　｜負責：C　｜check.js：會抓
- **會怎麼壞**：畫面用規則編號去查條文。查不到的話，整個右側明細都會當掉。

### 15. 法規原文不改，數字要查得到出處　｜負責：C　｜check.js：會抓
- **統一**：`regs/D0070115_*.md` 是從官方網站抓下來的原文，禁止修改。要用新條文時，從全國法規資料庫下載成新檔案，並在 `rules.json` 的 `source` 寫明出處。

## 畫面（D）

### 16. 模型裡的文字要跳脫才能放進畫面　｜負責：D　｜check.js：不會抓
- **會怎麼壞**：房間名稱裡如果有 `<`、`&` 這類符號，直接塞進 HTML 會讓畫面壞掉。
- **統一**：所有來自資料的文字都用 `esc()` 包起來再顯示。

## Git

### 17. 自動產生的檔案不 commit　｜check.js：會抓
- **會怎麼壞**：兩份網頁和 `sample-3` 是每個人 build 時產生的，每個人的都不一樣。commit 上去的話，每次合併都會衝突。
- **統一**：已經寫進 `.gitignore`，不要用 `git add -f` 強制加入。

### 18. 不 commit `.rvt`　｜check.js：會抓

### 19. 從 `team` 開分支，合併前先拉 `team`　｜check.js：不會抓
- **會怎麼壞**：從舊版本開始改，合併時會一次出現大量衝突。
- **統一**：開工前執行 `git pull origin team`。

### 20. 換行格式　｜已經自動處理
- `.gitattributes` 統一成 LF，Windows 和 Mac 混用也不會出現「整個檔案都被改過」的情況。

## 共用檔案：改之前要先在群組說

這些檔案是四個人之間的接口，改了會影響每個人：

- `docs/data-contract.md`（資料格式）
- `engine/review.js`、`build.js`（把大家的東西串起來的程式）
- `data/sample-1-模型快照.json`、`data/sample-2-專案設定.json`（大家開發時用的範例）

可以改，但要在群組講一聲，讓大家知道。改完的人要執行 `node check.js --relock`。
