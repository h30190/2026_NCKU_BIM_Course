# 逃生動線檢討：四人分工與時程（10/19～10/29）

我們是**一組四個人**，一起完成**一個作品**：Revit 逃生動線檢討工具。
四個人各負責作品的一部分，像接力一樣把資料傳下去：

```
 Revit 模型
    │
    ▼
 成員 A：從模型抓資料 ──► 成員 B：算路線和距離 ──► 成員 C：對照法規判斷 ──► 成員 D：做成畫面
 （外掛）                 （幾何）                 （法規）                 （前端）
```

10/29 23:59 前，四個人的成果合在一起，用**一個 PR** 交到課程 repo。

## 成員 A：Revit 外掛（姓名：＿＿＿＿）

**一句話：** 把 Revit 模型裡的房間、門、樓梯、走廊抓出來，存成 JSON。

**要交：**
- 外掛程式（放 `plugin/`）
- 用 專案1.rvt 抓出來的真實資料，格式照 `data/sample-1-模型快照.json`

**要注意：**

- 不確定的資料填 `null`，不要猜。例如門沒標淨寬、房間邊界沒封閉。
- 發現的問題寫進 `warnings`。

**交給：** 成員 B

## 成員 B：路線與距離（姓名：＿＿＿＿）

**一句話：** 拿 A 的資料，算出每間房最遠的點走到樓梯的路線和距離。

**要交：**
- 計算程式（放 `engine/`，可以從 `engine.js` 改起）
- 至少 3 間房的**手算核對**，誤差小於 0.1 m

**要算的東西：** 最遠點、路線、室內段距離、走廊段距離、總距離、每座樓梯各要走多遠、每個轉彎的角度。

**交給：** 成員 C

## 成員 C：法規判斷（姓名：＿＿＿＿）

**一句話：** 拿 B 算好的距離，對照法規判斷符不符合。

**要交：**
- `regs/rules.json`：逐條對照 `regs/` 裡的法規原文確認過
- 判斷程式和測試，例如 29.99 m → 符合、30.01 m → 不符合
- 找老師或建築師看過規則

**要注意：**
- 結果只能是四種：符合、不符合、需人工確認、模型資料不足。
- 自訂的保守值（接近上限 90% 等）標成「設計提示」，不算違法。

**交給：** 成員 D

## 成員 D：畫面與發表（姓名：＿＿＿＿）

## 怎麼同時做、最後再合併

```
dadajin666（我們這組的 fork）
│
├─ A-plugin    ← A 只改 plugin/
├─ B-engine    ← B 只改 engine/
├─ C-rules     ← C 只改 regs/
├─ D-frontend  ← D 只改 frontend/、README.md
│
└─ team        ← 四條分支合併到這裡 → 發 PR 給老師
```

**開工前（一次就好，10/20 前）**
1. dadajin666 的擁有者把另外三人加為 collaborator（GitHub → Settings → Collaborators）。
2. 一個人建好 `team` 分支和組資料夾，把這份檔案、`data/`、`regs/`、範例程式放進去，推上去。
3. 每個人從 `team` 開自己的分支。

**每天**
- 只改自己的資料夾，就不會跟別人衝突。
- 每天至少 commit 一次並 push 到自己的分支，別人才看得到進度。
- 開工前先把 `team` 最新的內容拉到自己的分支，例如別人改了 `data-contract.md`。

**合併（10/24 第一次、10/28 最後一次）**
1. 每個人從自己的分支發 PR 到 `team`，請另一位組員看過再按 merge。
2. 四條都合併後，在 `team` 上用 專案1.rvt 從頭跑一次。
3. 10/28 從 dadajin666 的 `team` 發 PR 到課程主 repo，標題寫「第X組 逃生動線檢討」。

**大家都要用到的檔案**（`data-contract.md`、`data/` 範例）：要改時先在群組講，由一個人改、發 PR，其他人再拉下來。

## 完成前檢查

- [ ] 同一個模型抓兩次，編號和數字都一樣。
- [ ] 資料有缺時，能指出是哪個元件。
- [ ] 至少 3 間房的距離有手算核對。
- [ ] 每條規則都寫了出處和測試；不確定的不會被判成符合。
- [ ] 點進任一間房，看得到路線、數字和條文依據。
- [ ] repo 裡沒有 `.rvt` 檔；所有東西都放在 `20261030/第X組_應用名稱/`。
